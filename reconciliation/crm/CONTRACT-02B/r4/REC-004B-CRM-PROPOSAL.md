## Scope

This document details CRM T1-B positions on schemas, error contracts, and wire compatibility for the Talent Read slice. It covers: exact wire shapes, error compatibility approach, and consumer/parser impact.

## 1. Transport and Endpoint

### 1.1 Transport Pattern

HRP T0 recommends: POST /api/integrations/crm/talent-context/query with CorrelationIdSchema.

CRM T1-B position: AGREED on POST + CorrelationId pattern. The exact path is HRP-proposed; CRM will consume whatever path HRP exposes. The path does not need to match this recommendation verbatim.

CRM does NOT request: GET methods, query-string parameters, or multi-step flows for this slice.

### 1.2 CorrelationId Semantics

HRP T0 recommends: correlationId generated by CRM, passed through, echoed in responses for tracing.

CRM T1-B position: AGREED. The correlationId is a tracing identifier, NOT an idempotency key. CRM generates it as corr-<safe>-<ts>-<rand>. HRP echoes it in responses for distributed tracing.

CRM does NOT use correlationId for deduplication or retry safety.

### 1.3 Request Size and Limits

HRP T0 has not specified request size limits.

CRM T1-B notes: fieldAllowlist has a maximum of 8 items per HRP recommendation. CRM will enforce this client-side. No other size limits are assumed.

## 3. Error Contract

### 3.1 Error Response Envelope (draft)

```json
{
  "schemaVersion": "1",
  "status": "FAILED",
  "correlationId": "corr-<safe>-<ts>-<rand>",
  "errors": [
    {
      "code": "<error code>",
      "messageKey": "<message key>",
      "retryClass": "NEVER | RETRY_SAFE | RETRY_UNSAFE"
    }
  ]
}
```

Note: schemaVersion='1', status='FAILED' are required. correlationId echoes the request correlationId.

### 3.2 Error Code Taxonomy

#### Base ContractError Codes (from frozen ContractErrorSchema)

| Code | HTTP | Trigger | Status |
|---|---|---|---|
| VALIDATION_ERROR | 422 | Malformed request, unknown field, schema violation | AGREED |
| AUTHENTICATION_REQUIRED | 401 | Missing/invalid/expired assertion | AGREED |
| FORBIDDEN | 403 | Insufficient permission, wrong org, delegation issue | AGREED |
| RATE_LIMITED | 429 | Rate limit exceeded | AGREED |
| DEPENDENCY_UNAVAILABLE | 503 | Replay store unavailable, HRP dependency down | AGREED |

#### Additive Codes (PROPOSED, pending REC-004b bilateral)

| Code | HTTP | Trigger | Status |
|---|---|---|---|
| NOT_FOUND | 404 | Hidden object or nonexistent object | PROPOSED |
| INTERNAL_ERROR | 500 | Unexpected server error, no PII/leak | PROPOSED |

## 4. Consumer/Parser Impact Analysis

### 4.1 CRM Error Parser Requirements

If additive global enum approach is chosen (CRM preference):

- CRM consumer parser must accept the extended error code union (existing codes + NOT_FOUND + INTERNAL_ERROR).
- Parser must handle unknown codes gracefully (treat as generic error, not crash).
- Exhaustive switch statements on error codes must be avoided in the consumer.

If query-local union approach is chosen (HRP preference):

- CRM must maintain a separate error parser for this query type.
- The query-local union is versioned; CRM must handle version transitions.
- Parser version must be coordinated with HRP schema version.

### 4.2 Versioning Approach

CRM T1-B preference: additive global enum (push NOT_FOUND/INTERNAL_ERROR into shared ContractErrorSchema).

Rationale:
- Single error parser for all integration endpoints.
- Standard HTTP semantics reduce learning curve.
- Shared taxonomy reduces maintenance burden.
- The change requires a shared contract package update (ACCEPTED_SHARED workflow).

Alternative: query-local union (HRP preferred). CRM can accept this if:
- The query-local union is versioned and stable.
- HRP provides a version identifier in the error envelope.
- CRM can detect version mismatches and fail safely.

### 4.3 messageKey Format

HRP T0 recommends: messageKey in format errors.talentContext.<code>.

CRM T1-B notes: messageKey is HRP-owned i18n key. CRM will use it for structured logging and optional UI display. messageKey format does not need bilateral sign-off; HRP owns the i18n namespace.

### 4.4 retryClass

HRP T0 recommends retryClass field in error responses.

CRM T1-B position: retryClass is AGREED as a concept. All defined error codes in this slice map to retryClass=NEVER (no retry). Future error codes may introduce RETRY_SAFE or RETRY_UNSAFE.

CRM does NOT use retryClass for automated retry logic in the read-only slice.

## 5. Open Items Requiring T0 Decision

### 5.1 Additive Enum vs. Query-Local Union

CRM T1-B proposes: additive global enum (NOT_FOUND and INTERNAL_ERROR into shared ContractErrorSchema).

HRP T0 proposes: query-local versioned union.

This is the primary open item for REC-004b. T0 CRM must accept or adjust the CRM position.

### 5.2 Exact Envelope Naming

The following names are HRP-proposed. Final naming requires bilateral confirmation:

- TalentContextReadQueryRequestSchema
- TalentContextReadTargetSchema
- TalentContextReadResultSchema
- TalentContextReadErrorResponse
- TalentContextReadField (enum)
- QueryAdditionalError (union member)

CRM does NOT require specific names; any stable, versioned names are acceptable.

## 6. CRM Implementation Obligations

Upon bilateral acceptance of REC-004b, CRM T1-B will implement:

- Request envelope construction matching the additive schema
- fieldAllowlist validation (required, non-empty, unique, max 8)
- Target validation (kind='TALENT', laborProfileId required)
- actor body construction (DELEGATED_USER, all fields present)
- Success response parsing (schemaVersion, correlationId, target, identitySummary, unavailableFields, resolvedAt)
- Projection filtering (omit unrequested, append unsupported to unavailableFields)
- Error response parsing (schemaVersion='1', status='FAILED', correlationId, errors array)
- Error code handling for all defined codes (VALIDATION_ERROR, AUTHENTICATION_REQUIRED, FORBIDDEN, RATE_LIMITED, DEPENDENCY_UNAVAILABLE, NOT_FOUND, INTERNAL_ERROR)
- CorrelationId tracing through request/response

CRM will NOT implement:
- Schema enforcement beyond consumer-side validation
- Server-side projection logic
- Error code registration
- messageKey resolution
