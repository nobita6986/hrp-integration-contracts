## M3 — Three parsers, isolated adapter directory

- `apps/integration-api/src/orchestrator/talent-context-read/parser-error.test.mjs`
- `apps/integration-api/src/orchestrator/talent-context-read/index.ts`
  (barrel export of the three parsers)

### What each parser does (corrected per C-03)
- `parseTalentContextReadRequest(raw)`:
  - `schema.safeParse(raw)`.
  - Returns a discriminated result:
    `{ ok: true; value: TalentContextReadQueryRequest }` or
    `{ ok: false; reason: "local-validation-failure"; issues: [...] }`.
  - Never fabricates an HRP wire error.
- `parseTalentContextReadResult(raw)`: same shape with
  `TalentContextReadResult`.
- `parseTalentContextReadError(raw)`: same shape with
  `TalentContextReadError`. Used only when the caller already has a
  payload that arrives from a real HRP response.

### Failure-mode taxonomy (corrected)
- "local-validation-failure" — parser-returned; NOT a wire error.
- "valid-hrp-error-envelope" — successful parse of an actual HRP error
  payload.
- "transport-runtime-failure" — raised exception; never fabricated.

### Imports
- Each parser imports the exact exported schema by name:
  ```
  import { TalentContextReadQueryRequestSchema } from
    "@hrp-engagement/contracts/talent-context-read/v1";
  ```
- No `dist/`, `src/`, or `internal/` paths.
- No duplication of any schema/type.

### Command
- `npm --prefix apps/integration-api run build`
- `npm --prefix apps/integration-api test`

### Acceptance criteria
- Each parser compiles with strict TypeScript settings.
- Each parser test asserts:
  - valid input parses and the discriminants are well-typed
  - malformed input returns `{ok:false, reason:"local-validation-failure"}`
  - HRP-error-shaped input parses via `parseTalentContextReadError`
  - transport failures propagate as exceptions (no synthetic
    payloads fabricated)
- Existing integration-api tests pass unchanged.

### Rollback
- Revert (delete) the seven new files.

### Risks
- A parser could accidentally import a private path. Mitigation:
  grep guard in CI test that asserts no `dist/`, `src/`, or
  `internal/` substring appears in any import of the new parsers.

### T0 gate
- G-03C.2 (parser separation; no synthetic HRP error).

### Local-only verification
- All runs locally. No provider needed.

### Port interface (planned)
```
type TalentContextReadPort = {
  read(req: unknown): Promise<
    | { ok: true; result: TalentContextReadResult }
    | { ok: false; reason: "local-validation-failure"; issues: [...] }
    | { ok: false; reason: "valid-hrp-error-envelope"; error: TalentContextReadError }
    | { ok: false; reason: "transport-runtime-failure"; cause: unknown }
  >;
};
```

### Mock implementation (planned)
- Deterministic.
- Every name goes through `redactFullName` from the accepted subpath
  BEFORE being placed in any result envelope.
- Result envelope never contains a raw PII string.
- Never fabricates a `valid-hrp-error-envelope`; HRP errors are only
  returned when the mock is configured to do so for testing.

### Route mock (planned)
- `HRP_MOCK_MODE=deterministic` OR an explicit `registerRouteMock()`
  factory call registers the route.
- The route enforces an actor/org boundary (configurable claim;
  default rejects) using parsed `QueryDelegatedUserActorSchema`.
- No default activation. The route is NOT registered at startup.

- `apps/integration-api/src/orchestrator/steps.ts`

### Command

### Acceptance criteria
- Port, mock, and route tests pass.
- Mock names are redacted in every output.
- Route mock only registered under `HRP_MOCK_MODE=deterministic` or
  via the explicit factory call.
- No canonical mutation is performed by the port or the route.
- intake-orchestrator test suite: unchanged pass/fail status.
