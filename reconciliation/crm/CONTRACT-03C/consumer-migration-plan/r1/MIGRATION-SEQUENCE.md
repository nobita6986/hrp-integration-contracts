### Command
```
npm --prefix <consumer> install <tarball-or-workspace>
```
Option A (workspace, post-publish):
  `npm install file:../../packages/contracts`
Option B (tarball, pre-publish):
  `npm install file:../../.scratch-pkg/hrp-engagement-contracts-0.0.0-r2-candidate.0.tgz`

### Acceptance criteria
- All six consumers `npm ci` (or `npm install`) cleanly.
- Every consumer builds: `npm run build` returns 0.
- Root export parity: 379/379 named exports identical to baseline.
- SCHEMA_VERSION, PACKAGE_VERSION unchanged from baseline.
- `git diff --stat` shows ONLY package.json + package-lock.json diffs,
  no source files.

### Rollback
- Revert the consumer package.json + package-lock.json. No source file
  was touched, so no source-file revert needed.

### Risks
- npm resolves differently when the tarball is unpacked at install time;
  this could surface the new subpath in node_modules even though the
  root surface is identical. Mitigated by the 379/379 export parity check.
- `file:` URL semantics may differ between npm 10.x and 11.x. T1-A
  verified compatibility evidence used npm bundled with Node 20.x.

### T0 gate
- T0 must confirm the candidate tarball identity (size, SHA-256, npm
  shasum, file count) before M1 is allowed to proceed.

### Local-only verification
- `npm install`, `npm run build`, `npm test` (non-PG) — all run on local
  Windows PowerShell. No Docker, no VPS.

## M3 — Add a CRM adapter for the talent-context-read contract

### Files (planned, all NEW)
- `apps/integration-api/src/orchestrator/talent-context-read-adapter.ts`
- `apps/integration-api/src/orchestrator/talent-context-read-adapter.test.ts`
  (or `.mjs` to match existing pattern)
- `apps/integration-api/src/orchestrator/index.ts` — re-export the adapter
  (if not auto-picked-up)

### What the adapter is
- A pure module that wraps:
  - `TalentContextReadQueryRequestSchema` — input parsing
  - `TalentContextReadResultSchema` — output validation
  - `TalentContextReadErrorSchema` — error classification
  - `QueryDelegatedUserActorSchema` — wrap delegatedUser identity
  - `MODULE_SCHEMA_VERSION`, `BACKEND_OPERATIONS`, `QUERY_ERROR_HTTP_STATUS`
- Adapter exports a function:
  ```
  parseTalentContextReadQuery(raw: unknown):
    | { ok: true; query: TalentContextReadQueryRequest }
    | { ok: false; error: TalentContextReadError }
  ```
- The adapter does NOT call any provider, mock, or runtime. It is a
  pure Zod parser over the new subpath.

### Imports
- `import * as TCR from "@hrp-engagement/contracts/talent-context-read/v1"`
- NO private, dist, src, or internal-path imports.
- NO duplication of any schema/type from the contracts package.

### Command
- `npm --prefix apps/integration-api run build`
- `npm --prefix apps/integration-api test`

### Acceptance criteria
- Adapter compiles with strict TypeScript settings.
- Adapter tests pass for:
  - positive: valid query parses to TalentContextReadQueryRequest
  - malformed assertion rejected
  - invalid delegation token rejected
  - unknown field rejected
- No tests fail that were green before M3.
- Adapter test does NOT require any provider, mock, or runtime.

### Rollback
- Revert (delete) the two new files. No existing file is modified.

### Risks
- Adapter could accidentally import a private path
  (e.g. `@hrp-engagement/contracts/dist/...`). Mitigation: explicit
  lint rule (or grep guard) that no `dist/`, `src/`, or `internal`
  appears in the new import paths.
- Adapter could shadow a root symbol. Mitigation: explicit no-conflict
  test that loads both the root and the subpath in the same process and
  asserts they coexist.

### T0 gate
- T0 reviews the adapter's API surface (one function in, one discriminated
  result out). T0 may require a specific function signature before M3.

### Local-only verification
- Full local build and test. No provider needed.

## M4 — Wire mock/local read path

### Files (planned)
- `apps/integration-api/src/orchestrator/talent-context-read-mock.ts` (new)
- `apps/integration-api/src/orchestrator/talent-context-read-mock.test.mjs` (new)
- `apps/integration-api/src/orchestrator/intake-orchestrator.ts` (edit: add
  optional `hrpRead` flag that, when set, calls the adapter and the mock
  instead of the existing local stub)
- `apps/integration-api/tests/orchestrator.test.mjs` (edit: add a
  TalentContextRead happy-path assertion)

### What the mock does
- Returns a deterministic TalentContextReadResult with:
  - subject: a hardcoded subject reference
  - availability: a hardcoded availability entry
  - redaction: calls `redactFullName` from the subpath
- Returns TalentContextReadError for malformed inputs.

### Imports
- The mock imports from the new adapter (M3) and the new subpath ONLY.

### Command
- `npm --prefix apps/integration-api run build`
- `npm --prefix apps/integration-api test`

### Acceptance criteria
- Mock returns a TalentContextReadResultSchema-valid result for valid
  inputs.
- Mock returns a TalentContextReadErrorSchema-valid error for invalid
  inputs.
- Existing intake-orchestrator behaviour unchanged when `hrpRead` is
  unset (default).
- When `hrpRead` is set to a mock provider, the orchestrator returns a
  TalentContextRead-shaped result envelope.
- No regression in any other orchestrator test.

### Rollback
- Revert (delete) the mock and the orchestrator wiring edit. Revert the
  orchestrator test addition. The adapter from M3 is preserved.

### Risks
- The mock could be mistaken for a real runtime path. Mitigation: the
  mock is gated behind an explicit `HRP_MOCK_MODE=deterministic` env
  var or an explicit `useMock` factory option. It is NEVER the default.
- Mock could leak PII if a real name is hardcoded. Mitigation: every
  mock name goes through `redactFullName` BEFORE being placed in the
  result. Result envelope never contains a raw PII string.

### T0 gate
- T0 confirms the mock is gated, not default, and the redaction is
  applied unconditionally.

### Local-only verification
- All runs locally. No provider. The mock IS the provider.
